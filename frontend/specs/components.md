## Tipos de API y props propuestas
Reutilizar `SummaryEntry` y `SummaryResponse` de [api-types.ts](api-types.ts), verificados contra `components.schemas.MetricsSummaryItem` y la respuesta array de `/api/metrics/summary`; no duplicar sus definiciones aqui. Reutilizar `SummaryParams` de [param-types.ts](param-types.ts), incluidas las fechas heredadas de DateRangeFilter. Query de `/summary`: agrupacion day/week/month, default month; enums de operaciones, categorias y grupos; filtros opcionales sin default explicito, nullable en OpenAPI, representados mediante omision. No enviar el texto "null".
Las definiciones completas de props siguientes existen SOLO como propuesta en este documento; no se crea component-types.ts. Los tipos API anteriores si estan declarados en sus archivos. `GroupApiData` es una agrupacion local de dos respuestas, no un nuevo envoltorio de endpoint. `CategoryShare` y `GroupPresentation` son datos derivados para presentacion, no respuestas API; percentage=null indica denominador cero. El vacio se deriva de respuestas exitosas, nunca de errores. Todos los callbacks describen interacciones futuras; App coordina los datos y los hijos no consultan.
```typescript
import type { FacetsResponse, AlertEntry, AlertsResponse, CategoryEntry, TopCategoriesResponse, SummaryResponse } from "./api-types";
import type { DateRangeFilter, AlertsParams } from "./param-types";
import type { BusinessType, Category, FinancialMovement, KPIMetrics, MonthlyDataPoint } from "../src/lib/financial-types";
type LoadState<T> = { status: "loading" } | { status: "error"; message: string } | { status: "success"; data: T };
type PageKey = "dashboard" | "comparativa";
interface GroupApiData { categories: TopCategoriesResponse; summary: SummaryResponse; }
interface CategoryShare { category: CategoryEntry["category"]; income: number; percentage: number | null; }
interface GroupPresentation { totalIncome: number; shares: CategoryShare[]; }
interface DashboardNavigationProps { activePage: PageKey; onNavigate: (page: PageKey) => void; }
interface DateRangeControlsProps { draft: DateRangeFilter; onDraftChange: (next: DateRangeFilter) => void; onApply: () => void; onClear: () => void; validationError: string | null; busy: boolean; }
interface DatasetRangeLabelProps { facets: LoadState<FacetsResponse>; onRetry: () => void; }
interface DashboardHeaderProps { period?: string; }
interface KPIRowProps { metrics: KPIMetrics | null; loading?: boolean; }
interface IncomeOutcomeChartProps { data: MonthlyDataPoint[]; loading?: boolean; }
interface ProfitPercentChartProps { data: MonthlyDataPoint[]; loading?: boolean; }
interface ThresholdControlProps { draft: string; value: number; error: string | null; busy: boolean; onDraftChange: (value: string) => void; onApply: () => void; }
interface AlertsTableProps { entries: AlertsResponse; }
interface AlertsPanelProps { params: AlertsParams; state: LoadState<AlertsResponse>; thresholdControl: ThresholdControlProps; onRetry: () => void; }
interface DashboardPageProps { range: DateRangeFilter; dateControls: DateRangeControlsProps; datasetRange: DatasetRangeLabelProps; movements: LoadState<FinancialMovement[]>; alerts: AlertsPanelProps; onRetryMetrics: () => void; }
interface B2BComparisonProps { range: DateRangeFilter; groups: Record<BusinessType, LoadState<GroupApiData>>; onRetry: (group: BusinessType) => void; }
interface ComparisonPageProps extends B2BComparisonProps { dateControls: DateRangeControlsProps; datasetRange: DatasetRangeLabelProps; }
interface BusinessCategorySectionProps { businessType: BusinessType; presentation: GroupPresentation; }
interface BusinessTotalsChartProps { totals: Record<BusinessType, number>; }
```
`AlertsTableProps.entries` conserva el array API de AlertEntry; sus porcentajes se formatean para mostrar, sin cambiar la respuesta. Cada pagina recibe en `range` su seleccion independiente y en `dateControls` su propio borrador/callbacks; las props de borrador no se serializan hasta validar. En DashboardPage, `movements` es API y KPIMetrics/MonthlyDataPoint[] son calculados; `alerts.params` contiene dashboardRange. En ComparisonPage, `groups` es API y usa comparisonRange; BusinessCategorySection y BusinessTotalsChart solo reciben presentacion derivada despues de validar coherencia y estado de las dos respuestas de cada grupo.
## 1. Filtro de fechas
**API verificada:** GET `/api/metrics` acepta `start_date` y `end_date` opcionales, string date nullable, y devuelve `FinancialMovement[]`. GET `/api/metrics/facets` no acepta filtros y devuelve `FacetsResponse`, con `min_date` y `max_date` globales. Los extremos son inclusivos por observacion; la API no documenta limites al rango del dataset ni exige inicio <= fin. Un rango invertido devuelve [] en las pruebas, no un error de validacion.
**Componentes propuestos:** `DateRangeControls` edita y valida fechas; props `draft: DateRangeFilter`, `onDraftChange: (next: DateRangeFilter) => void`, `onApply: () => void`, `onClear: () => void`, `validationError: string | null`, `busy: boolean`. `DatasetRangeLabel` muestra rango global; props `facets: LoadState<FacetsResponse>`, `onRetry: () => void`. App conserva rango aplicado y produce `KPIMetrics` y `MonthlyDataPoint[]` con las utilidades existentes; ningun hijo realiza consultas.
**Props existentes:** conservar `KPIRow(metrics: KPIMetrics | null, loading?: boolean)` y ambos graficos `(data: MonthlyDataPoint[], loading?: boolean)`. Reutilizar `DashboardHeader(period?: string)` pasandole siempre un rotulo calculado, sin recurrir al valor temporal fijo actual.
**Comportamiento propuesto:** dos entradas de fecha con etiquetas y acciones Aplicar/Limpiar. Fecha vacia equivale a propiedad omitida, nunca "", null ni "null" en query. Validar fecha civil real YYYY-MM-DD y orden antes de consultar. No restringir inputs al min/max de facets: mostrar ese rango como informacion global independiente de la seleccion. Aplicar en dashboard envia dashboardRange a metrics y alerts; no modifica ni consulta la comparativa. Threshold no cambia ni refresca KPI o comparativa.
**Estados propuestos:** carga con Skeleton en KPI/graficos y estado de carga propio del rango global; error de metrics con mensaje y reintento, sin tratarlo como cero; error de facets muestra "Rango disponible no disponible" y reintento sin impedir filtros validos. Vacio de metrics muestra "Sin movimientos en el rango seleccionado", cuatro KPI en cero (margen 0 %, convencion actual) y ambos graficos vacios, no curvas inventadas. Exito recalcula los cuatro KPI y ambas series solo a partir de movimientos filtrados.
**Criterios de aceptacion (propuestos; identificadores estables):**
- **DF-01:** probar cero, una y dos fechas en cada pagina; sus queries contienen solo limites no vacios de su propio rango en YYYY-MM-DD. Fecha imposible como 2026-02-30 muestra error local y no lanza consultas.
- **DF-02:** con inicio posterior a fin, Aplicar muestra error junto al filtro, no cambia el rango aplicado ni el encabezado de esa pagina y no dispara ninguna consulta; el rango de la otra pagina permanece intacto. Corregirlo permite aplicar.
- **DF-03:** facets se consulta sin fechas; su min/max se muestra como rango global. Seleccionar fechas fuera de el no se bloquea ni se recorta automaticamente.
- **DF-04:** un movimiento exactamente en cada extremo se incluye; cuatro KPI, dos graficos actuales y alertas usan dashboardRange. Aplicar o limpiar ese rango no modifica comparisonRange ni sus datos ni dispara consultas de top/summary. Una respuesta tardia de otro rango no reemplaza resultados actuales.
- **DF-05:** encabezado: sin limites muestra "Todo el dataset"; ambos limites "YYYY-MM-DD a YYYY-MM-DD"; solo inicio "Desde YYYY-MM-DD"; solo fin "Hasta YYYY-MM-DD". No permanece "2024 - Full Year" ni se sustituye la seleccion por fechas de los movimientos devueltos.
- **DF-06:** verificar Skeleton en carga, error con reintento sin datos falsos y fallo independiente de facets. Error en una consulta no convierte las otras en vacias ni muestra datos del rango anterior como actuales.
- **DF-07:** ante metrics=[], se muestran aviso, cuatro ceros y dos estados vacios; un reintento o cambio valido recupera el estado de exito con KPI/series calculados con las utilidades actuales.
## 2. Tabla de anomalias
**API verificada:** GET `/api/metrics/alerts` devuelve `AlertsResponse`. Usar `AlertsParams` con dashboardRange, `group_by="month"` (decision de agrupacion mensual alineada con los graficos), threshold aplicado y sin business_type para ambos grupos. API: threshold number >= 0, default 0.3, sin maximo documentado; group_by day/week/month, default month. No existen parametros de ventana de tres periodos.
**Componentes propuestos:** AlertsPanel usa AlertsPanelProps completas definidas arriba; `params` incluye las fechas aplicadas y `thresholdControl` transporta todo el estado/callbacks del control, sin perder el evento de cambio. ThresholdControl usa ThresholdControlProps y AlertsTable usa AlertsTableProps; filas AlertEntry, clave period para esta agrupacion y seleccion. No se duplica otro rango independiente dentro de AlertsPanel.
**Comportamiento propuesto:** cuatro columnas: Periodo (`period`), Outcome registrado (`outcome_total`), Media historica anterior (`baseline_average`), Incremento (%) (`increase_ratio * 100`). Orden cronologico de periodos; importes con formato actual y porcentaje con `formatPercent` tras multiplicar, sin multiplicar threshold al enviarlo. Interfaz valida numero finito 0.01 <= threshold <= 1.0, inicial 0.3; vacio, texto no numerico o fuera del intervalo muestra error y no consulta. Aplicar threshold solo actualiza alertas.
**Conflicto pendiente:** la tercera columna es la media de TODOS los periodos anteriores disponibles en el rango filtrado, no de los tres anteriores. La deteccion usa esa base, compara incremento estrictamente mayor que threshold y no evalua el primer periodo ni una base cero. El filtro recorta tambien los antecedentes; un mes aislado puede devolver [] aunque tenga egresos. No llamar a la columna "Media movil de tres periodos", no sustituir calculos en frontend como solucion aprobada y no declarar satisfecha toda la funcionalidad. AN-06 queda bloqueado; PM debe decidir si exige modificar el contrato/backend para una ventana de tres o aprueba formalmente cambiar el requisito. Si exige tres, aclarar antecedentes fuera del rango, periodos ausentes, historial insuficiente y base cero. El conflicto debe conservarse tambien en el futuro README de especificaciones, aun no redactado.
**Estados propuestos:** carga con estructura de tabla/Skeleton; error "No se pudieron cargar las anomalias" y reintento manteniendo parametros aplicados; vacio [] muestra "No se detectaron anomalias para el rango y umbral seleccionados", sin afirmar ausencia de movimientos; exito muestra las cuatro columnas con los valores reales, sin alterar la media recibida.
**Criterios de aceptacion (propuestos):**
- **AN-01:** valor inicial 0.3; 0.01 y 1.0 son validos en interfaz; 0, 1.01, vacio y no numerico bloquean Aplicar sin consulta. Documentar que API acepta 0 y valores >1, aunque la interfaz no.
- **AN-02:** cada fila muestra exactamente las cuatro columnas y conserva outcome_total/baseline_average de API; increase_ratio=1.0201 se muestra 102.0 % con el formato actual, no 1.0 %.
- **AN-03:** fechas aplicadas se incluyen u omiten igual que en metrics; al cambiar threshold solo se actualizan alertas. No se agregan parametros de ventana inventados ni se usan antecedentes externos silenciosamente.
- **AN-04:** [] produce el mensaje vacio explicito, incluso si metrics tiene movimientos; probar agrupacion de un solo mes sin historial, sin confundir ausencia de alertas con ausencia de egresos.
- **AN-05:** comprobar carga, error/reintento y exito para los mismos parametros; orden cronologico y ninguna fila del rango anterior durante carga o despues de respuesta obsoleta.
- **AN-06 (BLOQUEADO):** criterio propuesto, no prueba ejecutada: cumplir la media movil de los tres periodos anteriores y detectar con esa base. El ejemplo de marzo de 2026 corresponde exactamente a `start_date=2025-10-01`, `end_date=2026-03-31`, `group_by=month` y `threshold=0.3`, sin business_type, en summary/alerts (threshold solo en alerts). Outcome de diciembre=103378.98, enero=51690.68 y febrero=24863.08: media de tres=59977.58; la API observada usa octubre a febrero y devuelve 56456.19. No puede aceptarse con contrato actual; requiere decision explicita del PM y, si mantiene el requisito, cambio backend/contrato y nueva verificacion. AN-01 a AN-05 no desbloquean AN-06.
## 3. Comparativa B2B vs B2C
**API verificada:** por cada grupo consultar GET `/api/metrics/categories/top` con `TopCategoriesParams`: `operation_type="income"`, `limit=5`, `business_type="B2B"` o `"B2C"` explicitamente y comparisonRange. Respuesta `TopCategoriesResponse`, solo category/operation_type/total_amount. Defaults API: operation_type outcome y limit 5; limite entero 1-20. Hasta cinco categorias reales, no garantia de cinco; en la exploracion hubo solo sales y others por grupo.
**API verificada:** obtener ingresos de cada grupo mediante GET `/api/metrics/summary` con `SummaryParams`: `operation_type="income"`, `business_type` explicito, `group_by="month"` y comparisonRange, exactamente las mismas fechas que top para B2B y B2C; omitir category. Respuesta `SummaryResponse`; sumar `income` de todos los SummaryEntry, no `net`, para cada total. Aplicar o limpiar comparisonRange no modifica dashboardRange ni consulta metrics/alerts. Facets tiene categorias globales, no por grupo ni totales: nunca consultar facets con business_type ni inventar category por grupo, percentage o group_total en las respuestas. `/api/metrics` no acepta business_type.
**Conflicto de facets, no satisfecho:** el requisito de conocer categorias disponibles por grupo no puede acreditarse con `FacetsResponse.categories`, que es global y no distingue B2B/B2C, fechas ni operacion. Las categorias de top son solo las presentes en el ranking filtrado, no el catalogo completo disponible por grupo. BC-08 queda bloqueado: aclarar con PM si necesita un catalogo por grupo (y con que alcance temporal/operacion), lo que requiere contrato/API verificable adicional, o si acepta formalmente el catalogo global o solo las categorias devueltas por top. No hay alternativa aprobada ni parametros business_type para facets; mantener la tabla de top no satisface silenciosamente ese requisito.
**Componentes propuestos:** ComparisonPage contiene los controles y el rango global antes de B2BComparison. Usar ComparisonPageProps/B2BComparisonProps completas; `groups` conserva respuestas API separadas de GroupPresentation, derivada solo cuando top y summary del grupo estan completos para el mismo rango. BusinessCategorySection recibe BusinessCategorySectionProps, sin duplicar datos API y calculados; muestra Categoria/Ingresos/% del grupo y total. BusinessTotalsChart recibe BusinessTotalsChartProps con dos totales derivados; grafico Recharts unico, etiquetado B2B y B2C, no dos graficos ni series por categoria.
**Comportamiento propuesto:** secciones B2B y B2C paralelas en escritorio, apiladas en movil; no anidar cards. Mostrar solo categorias reales de top, conservar su orden por importe, no completar con categorias de facets ni ceros artificiales. Calcular porcentaje como `(entry.total_amount / totalIncome) * 100` sobre TODOS los ingresos del grupo; redondear solo al presentar. Si totalIncome=0, no dividir: percentage=null se representa "No calculable" cuando existan filas. Si top no vacio contradice total=0 con importes no cero, marcar inconsistencia y no mostrar porcentajes ni total como exito coherente.
**Estados propuestos:** carga independiente por grupo con Skeleton; grafico conjunto espera ambos grupos. Error de top o summary hace fallar ese grupo con mensaje/reintento, conserva el otro si corresponde al rango actual y deja el grafico en error, nunca convierte fallo en cero. Vacio top=[] y total=0 muestra "Sin ingresos para este grupo en el rango seleccionado" y total cero; ambos grupos vacios muestran sus dos ceros y "Sin ingresos para comparar" en lugar de barras ficticias. Exito muestra tablas/totales y el unico grafico; si solo un grupo es vacio, mantener su cero y la barra del otro. Top=[] con total distinto de cero es inconsistencia, no estado vacio; bloquear grafico y ofrecer reintento.
**Criterios de aceptacion (propuestos):**
- **BC-01:** inspeccionar cuatro queries por comparisonRange: top y summary para cada grupo, siempre income y business_type explicitos; top lleva limit=5; las cuatro usan fechas identicas; ninguna summary lleva category. Cambiar o limpiar fechas de comparativa no modifica dashboardRange, sus KPI/graficos/alertas ni dispara consultas de metrics/alerts.
- **BC-02:** con dos categorias devueltas se muestran dos filas, no cinco; con mas categorias disponibles top limita a cinco, sin inventar filas ni usar facets para completarlas. Columnas y total de cada seccion identifican inequivocamente su grupo.
- **BC-03:** con top que suma 600 y total de summary=1000, categoria de 300 muestra 30.0 %, no 50.0 %. Cambiar comparisonRange recalcula ambos denominadores y porcentajes, sin afectar al dashboard. Todos los income, y no solo los del top, participan.
- **BC-04:** grafico unico contiene exactamente B2B y B2C con las sumas de income de sus summaries, no sums del top ni net. En fixtures de exploracion sin fechas: B2B=615540.72 y B2C=642606.15; pruebas futuras deben fijar dataset/calendario, no asumir fechas inmutables.
- **BC-05:** probar menos de cinco, un grupo vacio, ambos vacios y denominador cero: no aparecen NaN/Infinity ni porcentajes falsos. Filas de importe cero con total cero muestran "No calculable"; contradicciones entre top y summary se tratan como error de consistencia.
- **BC-06:** carga y fallo parcial se muestran independientemente, con reintento del grupo; grafico no muestra cero para un grupo fallido ni mezcla rangos. Exito requiere top y summary coherentes de la misma seleccion para cada grupo.
- **BC-07:** escritorio presenta dos secciones paralelas y movil las apila sin ocultar columnas o etiquetas; navegar controles con teclado, errores asociados a inputs y estados accesibles. Ningun parametro o campo de categoria por grupo se atribuye a facets.
- **BC-08 (BLOQUEADO):** criterio propuesto, no prueba ejecutada: conocer las categorias disponibles de cada grupo. Facets global y top limitado no satisfacen ese catalogo; requiere aclaracion formal del PM sobre alcance y aceptacion de una alternativa, o ampliacion de contrato y verificacion. BC-01 a BC-07 no acreditan este requisito.
